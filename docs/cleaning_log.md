# Cleaning & Modeling Decision Log

Generated by `src/clean_data.py`. Each entry: what was done — and why.

- **Loaded 10,800 rows, 21 columns (latin-1 encoding)** — The file contains non-UTF8 characters in product names; latin-1 avoids decode errors without dropping rows.
- **Normalized column names to snake_case** — Consistent names prevent bugs in downstream SQL/BI tools and match common warehouse conventions.
- **Parsed order_date and ship_date as datetimes** — Dates arrive as strings in mixed US formats; typed dates enable time-series KPIs and shipping-lag checks.
- **Removed 505 exact duplicate rows (ignoring row_id)** — row_id is a surrogate key, so identical order lines with different row_ids are true duplicates that would double-count revenue.
- **Computed ship_lag_days; 0 rows ship before order date** — Negative lags indicate data-entry errors. Decision: flag rather than drop — the sales amounts are still valid for revenue KPIs, only the logistics metric is unreliable, so they are excluded from shipping analysis only.
- **Checked for non-positive sales: 0 rows** — Zero/negative sales would signal returns or errors needing separate treatment; none found, so no action required.
- **Derived profit_margin, order_month, discount_band** — Margin (not raw profit) is the comparable unit across products; discount bands turn a continuous variable into a decision-ready lever a manager can act on ('cap discounts at 20%'), which raw percentages don't.
- **Retained high-value outlier orders (max sale $22,638)** — In retail transaction data, large orders are real revenue, not noise. Winsorizing would understate the business. Dashboard charts use medians/aggregates that are robust to them instead.
